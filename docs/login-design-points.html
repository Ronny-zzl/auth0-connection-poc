個人／法人ログインの画面構成

Auth0 の Universal Login を使う前提で、ログイン画面をどう分担するかを決めたい。PoC の結果、決まったこと、まだ決める必要がある論点をまとめた。

PoC で確認できたこと

  • 個人と法人を別々の Database Connection に分け、connection パラメータで切り替える方式は Auth0 の標準機能で動く。
  • 同じメールアドレスでも、個人と法人は別ユーザー（sub が別）になる。パスワード、リセット、ロックもそれぞれ独立している。
  • connection はクライアント側で書き換えられる。認証後に、トークンの connection と選択したモードが一致するかの検証が必須。
  • 個人でログイン済みでも、法人を要求すると Auth0 がパスワードの再入力を求める。取り違えは起きない。

Universal Login を使うとログインはこう流れる

Universal Login は Auth0 がホストするログイン画面で、パスワードは Auth0 のドメインで入力する。アプリはパスワードに触れない。PoC のポップアップに出ていた画面がこれにあたる。

決まったこと

法人のログイン ID はメールアドレスで、法人間で重複させない

1 つのメールアドレスで持てる法人アカウントは 1 つだけ。複数の子会社で利用する人は、子会社ごとに別のメールアドレスを使う。法人番号＋ユーザー名＋パスワードの 3 項目ログインは採らない。

個人と法人は別の connection なので、同じメールアドレスで個人アカウントと法人アカウントを 1 つずつ持つことはできる（PoC で確認済み）。

法人アカウントはシステムが発行し、セルフサインアップは許可しない

申込フォームの送信後、法人管理者と各受検者のアカウントをまとめて発行する。corporate-database の Disable Sign Ups を有効にする。発行はバックエンドから Auth0 の Management API で行い、法人番号と役割（管理者／受検者）は app_metadata に持たせる。

受検者は全員メールアドレスを持ち、通知も本人に直接届く前提。パスワードを忘れたときは本人がメールでリセットできる。受検者が多い法人では、API を 1 件ずつ呼ぶとレート制限にかかるおそれがあるので、一括インポートも検討する。

ログイン画面は「Auth0 だと気づかれない」最低限の対応から始める

一般の利用者が、外部の認証サービスを使っていると意識しない状態を目指す。そのために必要な対応は次のとおり。

Auth0 が見える箇所対応条件
アドレスバーのドメインカスタムドメイン（例：auth.〇〇.jp）を設定するFree プランでも可。ただしクレジットカードの登録が必要（課金はされない）
ログイン枠の下の Auth0 の透かし非表示にする有料プランが必要（Free では消せない）
ログイン枠のロゴテーマエディタで自社ロゴに差し替えるFree でも可
色・フォント・角丸・背景テーマエディタで自社のデザインに合わせる（フォントは WOFF を指定）Free でも可
画面の文言すべての画面を日本語化し、テナント名などが出ないようにするFree でも可
メールの送信元とリンク自社のメール送信サービス（SMTP、SendGrid など）とメールテンプレートを設定する。リンクはカスタムドメインになるFree でも可
エラー画面テナント設定で自社のエラーページに転送する対象プランを確認する

この対応で、利用者からは「自社ロゴと配色のログイン画面」に見える。ただし、ログイン枠の中の部品は Auth0 のものなので、アプリのほかの画面とは細部の見た目が少し異なる。また、URL のパス（/u/login など）や開発者ツールで見えるスクリプト・Cookie からは、技術者なら Auth0 だと分かる。

Auth0 Organizations は使わない

法人数は 100 を超える見込みで、Organizations を無制限に使えるプランは費用が高い。法人のメールアドレスを重複させない方針にしたため、1 つのアカウントを複数の法人で使い分ける必要もない。

決めたいこと

Auth0 の画面で、個人と法人を見分けられるようにするか

PoC テナントで試したところ、文言のカスタマイズでは connection ごとに表示を変えられない。変数 ${connectionName} はデータベースのログイン画面では空になる。一方、アプリ名の ${clientName} は表示される。最低限の対応の範囲では、次の 2 案になる。

見分けない工数小

個人・法人とも同じログイン画面にする。直前のアプリ画面でモードは選んでいるので、混乱は少ないと考えられる。

アプリを個人用・法人用に分ける一部検証済み

Application を 2 つ作り、それぞれ 1 つの connection だけを有効にする。アプリ名が画面に出るので「法人ログイン」などと表示できる。

検証済み：別の connection を指定すると Auth0 が拒否する（the connection is not enabled）ので、connection の書き換えが効かない。connection を付けなくても正しい DB の画面になる。

代償：Client ID が 2 つになり、バックエンドは 2 種類の aud を受け付ける必要がある。

Page Templates と ACUL でも出し分けられるが、上の「完全に統一する場合」と同じ条件が要るので、今回は対象外とする。

パスワードをアプリの画面で入力させる必要はあるか

sample と同じ体験を残す案（Embedded Login）。Auth0 は推奨していない。

Universal Login に寄せる推奨

パスワードを扱わずに済む。パスキー、MFA、Bot 検知、ブルートフォース保護がそのまま使える。

アプリの画面で入力する

上の機能の多くを自前で補う必要がある。サードパーティ Cookie の制限の影響も受ける。採るなら理由を明確にしたい。

アカウント発行時に、メールアドレスが他の法人と重複していたらどうするか

法人のメールアドレスは重複させないので、すでに別の法人で使われているアドレスでは Auth0 にユーザーを作れない（API がエラーを返す）。どこで検知し、誰にどう伝えるかを決める。

申込フォームで検知する

入力時に「このメールアドレスは使用できません」と伝え、別のアドレスを入れてもらう。発行時の失敗はなくなるが、他の法人で登録済みだと推測できてしまうので、文言を工夫する。

発行処理で検知する

重複したユーザーだけ発行を保留し、法人の担当者に別のアドレスを依頼する。フォームは単純になるが、受検者の一部だけ発行が遅れる。

アカウント発行の通知メールに、初期パスワードを書くか

今の要件では、ログイン ID と初期パスワードを受検者本人にメールで送る。Auth0 には、本人にパスワードを設定してもらうリンク（Password Change Ticket）を発行する機能もある。

A. 初期パスワード（今の要件）B. パスワード設定リンク
メールの内容ログイン ID と初期パスワード（平文）ログイン ID と、パスワード設定のリンク
初回ログイン初期パスワードでログインしてから変更するリンクから自分で設定してからログインする
初回の変更強制強制するかどうかが未決。強制する場合、Auth0 に標準機能がないため、Post-Login Action と変更画面を自作する論点にならない。最初から本人が決めたパスワードになる
安全性メールを第三者に見られると、そのままログインされるリンクは 1 回限りで、有効期限がある
利用者の手間従来どおりで慣れているリンクの期限が切れたら再発行が必要

提案は B。通知メールの「初期パスワード」を「設定リンク」に置き換えるだけで、初回のパスワード変更を強制するかという論点がなくなる。A のまま変更を強制する場合は、その実装工数を見込む。

まだ確認できていないこと

  • どの有料プランで、Auth0 の透かしを消せるか。将来のために、Page Templates と ACUL の対象プランも合わせて確認する。
  • エラー画面を自社ページに転送する設定が、どのプランで使えるか。
  • アプリを分ける案で、2 つのアプリ間の SSO セッションの挙動と、実際のログインからトークン取得までの流れ。
  • PoC テナントは試用期間中で、Free プランにない機能も使える状態。プランを確認するときは、この点に注意する。
