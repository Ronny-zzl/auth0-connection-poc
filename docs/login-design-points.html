個人／法人ログインの画面構成

Auth0 の Universal Login を使う前提で、ログイン画面をどう分担するかを決めたい。PoC の結果と、決める必要がある論点をまとめた。

PoC で確認できたこと

  • 個人と法人を別々の Database Connection に分け、connection パラメータで切り替える方式は Auth0 の標準機能で動く。
  • 同じメールアドレスでも、個人と法人は別ユーザー（sub が別）になる。パスワード、リセット、ロックもそれぞれ独立している。
  • connection はクライアント側で書き換えられる。認証後に、トークンの connection と選択したモードが一致するかの検証が必須。
  • 個人でログイン済みでも、法人を要求すると Auth0 がパスワードの再入力を求める。取り違えは起きない。

Universal Login を使うとログインはこう流れる

Universal Login は Auth0 がホストするログイン画面で、パスワードは Auth0 のドメインで入力する。アプリはパスワードに触れない。PoC のポップアップに出ていた画面がこれにあたる。

決めたいこと

Auth0 の画面で、個人と法人を見分けられるようにするか

PoC テナントで試したところ、文言のカスタマイズでは connection ごとに表示を変えられない。変数 ${connectionName} はデータベースのログイン画面では空になる。一方、アプリ名の ${clientName} は表示される。

標準のまま工数小

Dashboard でロゴ・色・日本語の文言を設定するだけ。どちらのモードでも同じ画面になる。直前のアプリ画面でモードは選んでいるので、混乱は少ないと考えられる。

アプリを個人用・法人用に分ける一部検証済み

Application を 2 つ作り、それぞれ 1 つの connection だけを有効にする。アプリ名が画面に出るので「法人ログイン」などと表示でき、カスタムドメインも不要。

検証済み：別の connection を指定すると Auth0 が拒否する（the connection is not enabled）ので、connection の書き換えが効かない。connection を付けなくても正しい DB の画面になる。

代償：Client ID が 2 つになり、バックエンドは 2 種類の aud を受け付ける必要がある。

Page Templates で出し分け

Liquid テンプレートでログイン枠の周りを変える。カスタムドメインが必須（Dashboard 上でも、テンプレートの定義が先に必要と表示される）。設定は Management API からのみ。

ACUL で画面を作る

Auth0 の SDK を使って自前のフロントエンドで画面を作る。セキュリティ処理は Auth0 側のまま。Dashboard の Advanced mode で、カスタムドメインが必須と表示される。

パスワードをアプリの画面で入力させる必要はあるか

sample と同じ体験を残す案（Embedded Login）。Auth0 は推奨していない。

Universal Login に寄せる推奨

パスワードを扱わずに済む。パスキー、MFA、Bot 検知、ブルートフォース保護がそのまま使える。

アプリの画面で入力する

上の機能の多くを自前で補う必要がある。サードパーティ Cookie の制限の影響も受ける。採るなら理由を明確にしたい。

法人アカウントのセルフサインアップを許可するか決定

許可しない。法人のアカウントは、申込フォームの送信後にシステムが発行する（法人管理者と各受検者の分をまとめて）。そのため corporate-database の Disable Sign Ups を有効にする。

発行はバックエンドから Auth0 の Management API で行い、connection に corporate-database を指定する。法人番号と役割（管理者／受検者）は app_metadata に持たせる。PoC では、connection を指定するとその DB に登録され、指定しないと個人の DB に登録されることを確認している。

受検者は全員メールアドレスを持ち、通知も本人に直接届く前提。ログイン ID はメールアドレスでよく、パスワードを忘れたときも本人がメールでリセットできる。受検者が多い法人では、API を 1 件ずつ呼ぶとレート制限にかかるおそれがあるので、一括インポートも検討する。

カスタムドメイン（例：auth.〇〇.jp）を使うか

ログイン画面の URL が自社ドメインになる。Page Templates と ACUL の前提条件でもあるので、Q1 で出し分けを選ぶならセットで決める。

アカウント発行の通知メールに、初期パスワードを書くか

今の要件では、ログイン ID と初期パスワードを受検者本人にメールで送る。Auth0 には、本人にパスワードを設定してもらうリンク（Password Change Ticket）を発行する機能もある。

A. 初期パスワード（今の要件）B. パスワード設定リンク
メールの内容ログイン ID と初期パスワード（平文）ログイン ID と、パスワード設定のリンク
初回ログイン初期パスワードでログインしてから変更するリンクから自分で設定してからログインする
初回の変更強制強制するかどうかが未決。強制する場合、Auth0 に標準機能がないため、Post-Login Action と変更画面を自作する論点にならない。最初から本人が決めたパスワードになる
安全性メールを第三者に見られると、そのままログインされるリンクは 1 回限りで、有効期限がある
利用者の手間従来どおりで慣れているリンクの期限が切れたら再発行が必要

提案は B。通知メールの「初期パスワード」を「設定リンク」に置き換えるだけで、初回のパスワード変更を強制するかという論点がなくなる。A のまま変更を強制する場合は、その実装工数を見込む。

まだ確認できていないこと

  • Page Templates と ACUL が、どの料金プランで使えるか。ドキュメントに明記がないので Auth0 に確認する。
  • アプリを分ける案で、2 つのアプリ間の SSO セッションの挙動と、実際のログインからトークン取得までの流れ。
  • PoC テナントは試用期間中（残り約 3 週間）で、Free プランにない機能も使える状態。料金プランを確認するときは、この点に注意する。
  • Auth0 Organizations で法人を管理する方式との比較。
