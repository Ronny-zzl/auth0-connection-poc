個人／法人ログインの画面構成

Auth0 の Universal Login を使う前提で、ログイン画面をどう分担するかを決めたい。PoC の結果と、決める必要がある論点をまとめた。

PoC で確認できたこと

  • 個人と法人を別々の Database Connection に分け、connection パラメータで切り替える方式は Auth0 の標準機能で動く。
  • 同じメールアドレスでも、個人と法人は別ユーザー（sub が別）になる。パスワード、リセット、ロックもそれぞれ独立している。
  • connection はクライアント側で書き換えられる。認証後に、トークンの connection と選択したモードが一致するかの検証が必須。
  • 個人でログイン済みでも、法人を要求すると Auth0 がパスワードの再入力を求める。取り違えは起きない。

Universal Login を使うとログインはこう流れる

Universal Login は Auth0 がホストするログイン画面で、パスワードは Auth0 のドメインで入力する。アプリはパスワードに触れない。PoC のポップアップに出ていた画面がこれにあたる。

決めたいこと

Auth0 の画面で、個人と法人を見分けられるようにするか

標準の設定（ロゴ・色・文言）では、connection ごとに表示を変えるのは難しい。「法人ログイン」と出したいなら、追加のカスタマイズが要る。

標準のまま工数小

Dashboard でロゴ・色・日本語の文言を設定するだけ。どちらのモードでも同じ画面になる。直前のアプリ画面でモードは選んでいるので、混乱は少ないと考えられる。

Page Templates で出し分け

Liquid テンプレートでログイン枠の周りを変える。カスタムドメインが必須。設定は Management API からのみ。

ACUL で画面を作る

Auth0 の SDK を使って自前のフロントエンドで画面を作る。セキュリティ処理は Auth0 側のまま。カスタムドメインが必須。

パスワードをアプリの画面で入力させる必要はあるか

sample と同じ体験を残す案（Embedded Login）。Auth0 は推奨していない。

Universal Login に寄せる推奨

パスワードを扱わずに済む。パスキー、MFA、Bot 検知、ブルートフォース保護がそのまま使える。

アプリの画面で入力する

上の機能の多くを自前で補う必要がある。サードパーティ Cookie の制限の影響も受ける。採るなら理由を明確にしたい。

法人アカウントのセルフサインアップを許可するか

PoC では、connection を指定すればその DB に登録され、指定しないと個人の DB に登録された。法人アカウントを管理者が発行する運用なら、corporate-database のサインアップを止められる。

カスタムドメイン（例：auth.〇〇.jp）を使うか

ログイン画面の URL が自社ドメインになる。Page Templates と ACUL の前提条件でもあるので、Q1 で出し分けを選ぶならセットで決める。

まだ確認できていないこと

  • Page Templates と ACUL が、どの料金プランで使えるか。ドキュメントに明記がないので Auth0 に確認する。
  • 文言のカスタマイズだけで、connection ごとに表示を変えられるか。必要なら PoC テナントで試す。
  • Auth0 Organizations で法人を管理する方式との比較。
